# Menú técnico: Markdown y HTML básico → fragmento HTML

**Recomiendo combinar `markdown-it-py` para interpretar Markdown y `nh3` para conservar únicamente el HTML permitido.** Son dos piezas con una unión pequeña: una cadena de texto entra al parser, su HTML pasa al sanitizador y sale el fragmento que consume la previsualización. Nuestro código definiría la política del producto y esa conexión.

Entiendo que buscas una herramienta local pequeña en Python, sin servicios externos, para documentos de terceros. Asumo Python 3.10 o superior y contenido básico: títulos, párrafos, listas, enlaces, código y formato HTML sencillo. Las imágenes, estilos propios, extensiones de Markdown y enlaces relativos necesitan una política explícita; no los activaría por accidente. Esta propuesta es para elegir piezas: no he instalado ni integrado nada.

En esta herramienta usaría paquetes y configuración selectiva: copiar sus parsers o mantener forks no aporta una simplificación útil a este alcance. Tampoco hace falta añadir un framework web, una base de datos, un sistema de plugins o un tercer repo para unirlos. `argparse` y la lectura/escritura de UTF-8 pueden resolverse con la biblioteca estándar si queremos un CLI.

**Por qué elijo A.** La interfaz `MarkdownIt.render` conecta directamente con `nh3.clean`; no hay esquemas que reconciliar, autenticación ni estado persistente compartido. He comprobado un detalle decisivo: el renderer devuelve el HTML embebido tal cual. Por eso el filtrado se aplica **después** del render y antes de presentar el documento; el parser por sí solo no cubre este requisito. La documentación del propio parser describe esa combinación para contenido no confiable. [API del parser](https://github.com/executablebooks/markdown-it-py/blob/6f586542653a56d2ee8549a0dccfaa6ba5ebe14a/markdown_it/main.py), [renderer](https://github.com/executablebooks/markdown-it-py/blob/6f586542653a56d2ee8549a0dccfaa6ba5ebe14a/markdown_it/renderer.py), [seguridad](https://github.com/executablebooks/markdown-it-py/blob/6f586542653a56d2ee8549a0dccfaa6ba5ebe14a/docs/security.md), [API de nh3](https://github.com/messense/nh3/blob/5910b4c1ecbe9ccb53c0b94018d265cad5c80d06/src/lib.rs).

La deuda que podemos evitar es concreta: no ser propietarios de otro parser casero con reglas incompletas, ni de una colección creciente de expresiones regulares para quitar HTML peligroso. En el parser ya hay un test para secuencias de HTML sin cerrar que anteriormente provocaban trabajo cuadrático; en `nh3` hay tests de atributos de evento y eliminación de contenido `script`/`style`. Aprovechamos ese trabajo, pero los tests inspeccionados no prueban todavía nuestra configuración. Nos quedan la política de contenido, las pruebas de la unión y las actualizaciones de dependencias. [Test del parser](https://github.com/executablebooks/markdown-it-py/blob/6f586542653a56d2ee8549a0dccfaa6ba5ebe14a/tests/test_html_inline.py), [tests de nh3](https://github.com/messense/nh3/blob/5910b4c1ecbe9ccb53c0b94018d265cad5c80d06/tests/test_nh3.py).

**Plan de integración propuesto:**

1. Fijar el contrato `render_fragment(markdown: str) -> str` y qué HTML básico preservamos. Definir aparte enlaces relativos e imágenes: filtrar HTML no garantiza por sí solo que la previsualización no haga solicitudes de red.
2. Elegir versiones publicadas que correspondan a las capacidades inspeccionadas, comprobar instalación binaria de `nh3` en el entorno objetivo y registrar versiones y hashes. Los commits estudiados son evidencia de código, no una selección de releases ya probada.
3. Conectar `MarkdownIt("commonmark", {"html": True}).render(...)` con `nh3.clean(...)`. Mantener configuración explícita; sin extras del parser, highlighting ni atributos arbitrarios. No compartir entre documentos el diccionario de entorno del parser.
4. Probar la unión con documentos que combinen encabezados, listas, código, `<b>` y `<br>`; comprobar que conserva el formato acordado y filtra `script`, eventos como `onerror`, URLs no permitidas y HTML mal formado. Incluir un documento grande y un caso de HTML sin cerrar. La primera prueba debe demostrar simultáneamente formato conservado y filtrado correcto.
5. Añadir el adaptador local de archivos o stdin/stdout, errores claros y un límite razonable de entrada. Insertar el resultado únicamente como fragmento del cuerpo HTML: no reutilizarlo dentro de atributos o scripts.
6. Guardar atribución, versiones y decisiones; conservar avisos originales y revisar las dependencias transitivas al empaquetar. Cada actualización volverá a ejecutar nuestro corpus de documentos y pruebas del filtrado.
